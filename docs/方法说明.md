# 方法说明（每一步怎么做、口径是什么）

> 这份文件是**面试时可以直接讲**的版本：为什么这么做、怎么验证做对了。

---

## 第 0 步：为什么不用现成工具

目标不是「找到岗位」，而是**按我自己的经历库加权**，并让整条链路（取数 → 清洗 → 匹配 → 出简历）都可控、可复现。
现成求职工具不暴露口径，也无法接入我自己的经历标签体系。

---

## 第 1 步：取数（`01_extract_feishu.js`）

**遇到的问题**：目标数据在一个飞书多维表格里，界面是 canvas 渲染的——**DOM 里根本没有文字**，复制、截图、OCR 都不行。
直接 `curl` 它的数据接口返回 `{"code":5,"msg":"Login Required"}` —— 需要页面会话 Cookie。

**做法**：在页面自己的上下文里执行 `fetch`（同源、自动带 Cookie），复用页面自身的数据接口。
- 字段元数据接口拿到 18 个字段的定义与选项标签
- 记录接口按 `offset` 分页（单页上限 3000），三次取完 **7,855 条**
- 返回的 `data.records` 是 **base64(gzip(json))**：在页面内 `atob` → `Uint8Array` → `DecompressionStream('gzip')` 解出来
- 解出来的文本 POST 到本机一个临时 HTTP 服务落盘（跨域只发不读，用 simple request 绕开预检）

**关键判断**：`tableRecordNum` 字段告诉我们总记录数，用它校验「取全了没有」——3000+3000+1855 = 7855 ✅

---

## 第 2 步：清洗建库（`02_build_records.py`）

1. 把 base schema 也从 base64+gzip 里解出来，拿到 `fieldMap`：**字段 ID → 中文名**、**选项 ID → 标签**
2. 合并三个分页的 `recordMap`，按 `recordID` 去重
3. 逐条还原：文本/链接取 `text`/`link`；多选取数组拼 `|`；日期字段是毫秒时间戳，转成 `YYYY-MM-DD`

**验证**：输出 7,855 行 × 18 列，与 `tableRecordNum` 一致。

---

## 第 3 步：筛选与排序（`03_filter_rank.py`）

**必过条件**：届次含「2027 届」。

**技能匹配打分**（因为岗位字段是整包文本，只能做词频近似）：
- 正向词计分：数据分析 / 商业分析 / 数据科学 / 数据挖掘 / 经营分析 / 统计分析 / 运营 / 产品经理 / 管培 / 研究 / 风控 …
- 负向词扣分：研发 / 算法 / 工艺 / 机械 / 土木 / 芯片 / 嵌入式 …
- 净分 = 正向数 − 2 × 负向数（负向权重取 2，因为整包文本里技术词更容易误命中）
- **★ 标记**：JD 中**明确出现**「数据分析｜商业分析｜数据科学｜数据挖掘｜经营分析｜统计分析｜数据运营｜数据产品｜数据治理」——这是最高置信度的一档

**去重口径**：公司名规范化（去空格、去括号内容、去「集团/有限公司/股份有限公司/中国」等后缀）后比对，**同一公司取最高分那条**。

**验证**：★ 档 65 家；人工抽查 30 家，与岗位文本判断一致。

---

## 第 4 步：交付（`outputs/`）

- 第一批 50 家的短名单（含投递链接、截止日、该用哪版简历）
- 全量岗位库 xlsx（3 个 sheet：全部 / 候选池 / 短名单）

## 人的部分 vs AI 的部分（面试必问）

| 环节 | 谁做的 |
|---|---|
| 定义要什么数据、字段口径、验收标准（记录数要对得上） | **人** |
| 判断「取的这份表是不是有用的那份」（版本1 vs 版本2） | **人** |
| 发现 canvas 渲染取不到文字、接口要 Cookie、数据是 gzip 的 | 人提出要求，AI 试错定位 |
| 写取数脚本、解压、字段还原、打分排序的代码 | **AI 执行** |
| 校验结果（7,855 对不对、★ 档抽查合不合理） | **人** |
| 迭代（第一版打分把土木类排到了前面 → 退回重写负向词） | **人提出，AI 改** |

**一句话版本**：我负责「要什么、算不算对、下一步改什么」，AI 负责「怎么写出来」。
